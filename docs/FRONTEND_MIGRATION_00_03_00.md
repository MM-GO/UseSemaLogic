# Frontend migration guide — SemaLogic API 00.02.x → 00.03.00

Change period: 2026-07-31 to 2026-07-31

For the agent adapting the frontend. Every example below was captured from a
running 00.03.00-01 service, not written from memory.

**The one sentence version:** `/rules/parse` and `/rules/show` no longer return
HTML, SVG or Canvas as the response body. Every reply is now one JSON envelope,
and your markup has to be *extracted* from it — but in exchange every reply also
carries structured diagnostics you can filter, group and act on.

---

## 1. What breaks, exactly

Only the **response bodies** of `/rules/parse` and `/rules/show` change. No
path, parameter or request body you use today stops working (see §6).

### Before (00.02.x) → after (00.03.00)

| rulesettype | old Content-Type | old body | new location of that same content |
| --- | --- | --- | --- |
| `ASP.json` | `application/json` | `{rules, rulesettype, errors}` | `rules` (unchanged array) |
| `SemaLogic` | `text/html` | raw markup | `rules.html` |
| `SemanticTree` | `text/html` | raw markup | `rules.html` |
| `SVG` | `application/xml` | raw `<svg>` | `rules.svg` |
| `KnowledgeGraph` | `application/json` | raw Canvas doc | `rules.canvas` (a **string**) |
| `DialectEngine` | `application/json` | `{rulesettype, rules}` | unchanged, plus `diagnostics` |
| `AnnotatedHTML` | *(new)* | — | `rules.html` |

**The Content-Type is now `application/json` for all of them.** If your code
branches on Content-Type, or hands the body straight to `innerHTML` / an
`<img src>` / `JSON.parse`, that is what has to change.

### The envelope

```json
{
  "rulesettype": "SemanticTree",
  "rules":       { … payload, see §2 … },
  "diagnostics": { "items": [ … ], "summary": { … }, "groups": [ … ] }
}
```

- `rulesettype` — echoes what you asked for. **May be absent** on a request
  rejected before an output format was chosen (see §5).
- `rules` — the payload; `null` on the error path.
- `diagnostics` — **always present**, including on a completely clean parse.

## 2. Extracting the payload

Pick the branch by `rulesettype`. There is no JSON discriminator inside `rules`
(one branch is an array and cannot carry a marker), so read the sibling field.
The spec records the mapping as `x-rulesettype-mapping` on `rulesout.rules`.

```ts
type Rulesout = {
  rulesettype?: string;
  rules: unknown | null;
  diagnostics: Diagnostics;
};

function extract(res: Rulesout): { kind: string; content: string | unknown } {
  switch (res.rulesettype) {
    case "SemaLogic":
    case "SemanticTree":
    case "AnnotatedHTML":
      return { kind: "html", content: (res.rules as RulefmtHtml).html };
    case "SVG":
      return { kind: "svg", content: (res.rules as RulefmtSvg).svg };
    case "KnowledgeGraph":
      // NOTE: a JSON *string*, not an object. Parse it yourself.
      return { kind: "canvas", content: JSON.parse((res.rules as RulefmtKnowledgeGraph).canvas) };
    case "ASP.json":
      return { kind: "asp", content: res.rules };          // array, unchanged
    case "DialectEngine":
      return { kind: "engine", content: (res.rules as RulefmtDialectEngine).output };
    default:
      return { kind: "none", content: null };              // rules === null
  }
}
```

### Verified payload shapes

`SemaLogic` and `SemanticTree` — both `rulefmt_html`:

```json
{ "html": "<font style=\"color:#f8f8f8;\">…", "fragment": true,
  "mediaType": "text/html", "dialectID": "default" }
```

```json
{ "html": "\n<!DOCTYPE html>\n<html lang=\"en\">…", "fragment": false,
  "mediaType": "text/html", "dialectID": "default" }
```

**`fragment` is the field you must respect.** `SemaLogic` returns `true` — a
snippet you insert into existing DOM. `SemanticTree` returns `false` — a whole
`<!DOCTYPE html>` document, which belongs in an iframe/new window, not in
`innerHTML`. You could not tell these apart from the markup before.

`SVG` — `rulefmt_svg`:

```json
{ "svg": "<?xml version=\"1.0\"?>\n<!-- Generated by SVGo -->…", "mediaType": "image/svg+xml" }
```

`KnowledgeGraph` — `rulefmt_knowledgeGraph`. `canvas` is a **JSON string**:

```json
{ "canvas": "{\n  \"nodes\": [ … ], \"edges\": [ … ]\n}", "view": "user" }
```

`AnnotatedHTML` (new) — `rulefmt_annotatedHTML`:

```json
{ "html": "<div class=\"sl-annotated\"><section class=\"sl-text\" data-sl-textid=\"t1\"> A [B,C,D]</section></div>",
  "fragment": true, "mediaType": "text/html", "source": "echo", "textID": "t1" }
```

> `source: "echo"` means the endpoint currently just returns your input text
> wrapped in minimal HTML. The real annotator is not wired up yet. **Do not
> build UI that assumes real annotation markup** — when it lands, `source`
> becomes `"annotate"`. Branch on that field.

### Escaping

The markup arrives as a JSON string, so it is JSON-escaped in transit and your
JSON parser unescapes it. It is **not** HTML-escaped: it is markup meant to be
rendered. Treat it exactly as you treated the old raw body, including whatever
sanitising you already do.

## 3. Diagnostics — the actually new capability

`diagnostics` is always present. On a clean parse:

```json
{ "items": [], "summary": { "defect": 0, "suspect": 0, "note": 0, "blocking": 0, "hidden": 0 } }
```

So you can render a finding count unconditionally — no null check.

### One finding

```json
{
  "audience": "user",
  "severity": "defect",
  "message":  "OR term \"a\" declares max 5 but only 2 option(s) are available",
  "errortext":"OR term \"a\" declares max 5 but only 2 option(s) are available",
  "code":     "knowledge.val_concept_or_cardinality.MaxExceedsOptions",
  "id":       "4d8544592cc0a367b63feeb6f92b32b0efc3431dc77d69f61311a47f9202460b",
  "subject":  { "symbol": "a" }
}
```

| Field | Always? | Use it for |
| --- | --- | --- |
| `message` | **yes** | what you show the user |
| `errortext` | yes | **deprecated** duplicate of `message`; ignore it in new code |
| `severity` | **yes** | `defect` \| `suspect` \| `note` \| `blocking` — colour, icon, sort order |
| `audience` | **yes** | `user` \| `developer` — see §4 |
| `code` | no | stable id for "explain this", per-code muting, i18n |
| `id` | no | content-addressed → dedup, "don't show again" that survives reloads |
| `subject.symbol` | no | which symbol it is about → highlight / jump to it |
| `origin` | only `audience=developer` | package/file/func/line, dev overlay only |

**`code`, `id`, `subject` and `origin` are optional and frequently absent.**
Only a minority of engine producers emit structured findings today; the rest
arrive as a rendered sentence with `message`, `severity` and `audience` only.
Design for that: `message` + `severity` is the baseline, the rest is enrichment.
Never key a required UI path off `code` being present.

### `summary` counts more than `items`

`summary` counts the **complete** finding set — including what the audience
filter withheld. `hidden` is the difference. Live example, same request, only
the `audience` parameter differs:

```
default (user):      items: 1   audiences: [user]
                     summary: {defect:1, note:2, suspect:0, blocking:0, hidden:2}

audience=developer:  items: 3   audiences: [user, developer, developer]
                     summary: {defect:1, note:2, suspect:0, blocking:0, hidden:0}
```

That is the whole point: with the default call you can render

> ⚠ 1 problem — *show 2 technical messages*

and fetch those two only when the user clicks, by repeating the request with
`audience=developer`. You never hold developer noise you are not showing.

### `groups`

Present only when findings carry a `code`. Repeated findings collapse:

```json
"groups": [ { "code": "knowledge.val_concept_or_cardinality.MaxExceedsOptions",
              "count": 1,
              "ids": ["4d854459…"] } ]
```

Render one row with a count instead of N identical rows; `ids` links back to the
matching `items`.

### Suggested UI mapping

| severity | meaning | suggestion |
| --- | --- | --- |
| `blocking` | could not be interpreted at all | error, block the action |
| `defect` | certainly wrong | error |
| `suspect` | probably wrong (heuristic) | warning, dismissible |
| `note` | informational | info, collapsed by default |

Severity is confidence, **not** "did it fail" — SemaLogic proceeds with the most
defensible reading, so you can get a `defect` together with a usable `rules`
payload. Render both.

## 4. The `audience` parameter

New optional query parameter on `/rules/parse`, `/rules/show`, `/rules/define`:

- `audience=user` — the default. Only findings about the submitted ruleset.
- `audience=developer` — everything, plus `origin` on each finding.

Anything else (including a typo) falls back to `user`, so a bad value never
leaks internals. Use `developer` for an admin/debug view only.

---

## 5. The error path uses the same envelope

Previously there were three different error shapes, two undocumented. Now there
is one. Verified 422:

```json
{ "diagnostics": { "items": [ { "audience": "user", "severity": "defect",
      "message": "0.main.server.SemaLogic.739: System: engine \"dialectgen_v1\" currently requires rulesettype \"DialectEngine\", got \"ASP.json\"" } ],
    "summary": { "defect": 1, "suspect": 0, "note": 0, "blocking": 0, "hidden": 0 } },
  "rules": null }
```

Note: `rules` is `null` and **`rulesettype` is absent** — the request never got
as far as choosing an output format. So:

- Use *one* decoder for 2xx and 4xx alike.
- Treat `rulesettype` as optional; do not index into a map with it unguarded.
- Do not rely on the HTTP status to find the reason — read `diagnostics.items`.
- Some messages still carry an engine-ish prefix (`0.main.server.…: System:`).
  That is cosmetic and being cleaned up upstream; do not parse it.

## 6. Renames — nothing you use breaks

Canonical spellings were introduced; **every old form is kept as a permanent
alias** and behaves identically. Migrate when convenient, not urgently.

| Old (still works) | New canonical |
| --- | --- |
| `GET /APIVersion` | `GET /api-version` |
| `DELETE /StopServer` | `DELETE /stop-server` |
| `GET /rules/progress` | `GET /session/progress` |
| `?NLP=true` | `?nlp=true` |

`NLP` is only read when `nlp` is absent — do not send both. Query parameter
names are case sensitive, which is why the old uppercase spelling was a
recurring source of bugs.

Unchanged: `sid`, `view`, `engine`, all request bodies, and `parsedata.interprete`.

---

## 7. Migration checklist

1. Stop branching on `Content-Type`; it is `application/json` everywhere now.
2. Replace "body → render" with "body → `JSON.parse` → `extract()` (§2) →
   render".
3. Honour `fragment`: `false` means a full document (`SemanticTree`), not a
   snippet.
4. `KnowledgeGraph.canvas` needs a second `JSON.parse`.
5. Read findings from `diagnostics.items`, not from `errors` — that field is
   gone. Use `message`, not `errortext`.
6. Show `summary` counts even when `items` is empty.
7. Add the "show N technical messages" affordance driven by `summary.hidden`,
   loading them with `audience=developer`.
8. Use one decoder for success and error; guard for `rules: null` and a missing
   `rulesettype`.
9. Treat `code` / `id` / `subject` as optional enrichment.
10. Branch `AnnotatedHTML` rendering on `source` (`echo` today, `annotate`
    later).
